# DICOMをプロジェクトへ取り込む

[アノテーション操作](README.md) / [追加機能の一覧](../README.md)

DICOMの画像データから、CVATの静止画タスクまたは動画タスクを作成する機能です。患者IDや検査条件も、各画像に付けるタグ **DicomTag** として保存します。「DicomTag」は、後からレポートを照合したり、画素間隔から長さを計算したりする際にも使います。

## 取り込みの操作

1. プロジェクトのActionsで `DICOM import` を開きます。
2. フォルダまたはファイルを選択するか、画面へドロップします。下位フォルダも探索し、DICOMファイル、ZIP、TAR、TAR.GZ、TGZを取り込みます。
3. ドロップ領域の下にある接頭辞欄に、データの提供元などを示す文字列を入力します。必須項目で、例えば `GRD` と指定します。
4. 登録を実行します。転送中は、サーバーが受け取った容量と完了ファイル数を表示します。
5. 「登録を受け付けました。」と表示されたら、画面を閉じられます。以後のヘッダー確認、画像変換、タスク登録はRequestsで確認します。

転送完了後は「サーバーの受付を確認中」と表示します。この段階では画面を開いたままにしてください。転送の完了と、サーバーが取り込みを受け付けたことを区別するため、受付を確認するまで完了表示にしません。ページの再読み込みやタブを閉じる操作には、ブラウザー標準の確認を要求します。

通信が途切れた場合は、同じ画面の「転送を再開」から続行できます。サーバーは受信位置と再送部分の内容を照合し、同じデータを重ねて追記しません。受付の応答だけが確認できない場合は「受付を再確認」を使います。同じ転送の受付を繰り返しても、取り込み処理を二重に開始しません。再読み込み後や、閉じた画面を開き直した後の転送再開には対応していません。

完了時には結果の件数を通知します。一部のタスクだけが失敗した場合は警告、全タスクが失敗した場合はエラーです。取り込みダイアログを閉じても、受け付け済みの処理と結果の監視は継続します。転送を中止する操作は、既に受け付けた取り込み処理を取り消しません。

通知の監視は、ブラウザーを再読み込みすると終了し、以後はCVAT標準の通知になります。アカウントや組織を切り替えた場合も、以前の操作に対する通知を表示しません。処理結果はRequestsで確認してください。

## タスク名とファイル名

DICOMには、検査を識別する `StudyInstanceUID` と、個々の画像データや動画を識別する `SOPInstanceUID` があります。以下の名前では、それぞれの末尾だけを使います。完全な値は「DicomTag」に保存します。

画像と動画のファイル名は次の形式です。SOPInstanceUIDはピリオドを除去した末尾8文字、InstanceNumberは4桁へのゼロ埋めです。接頭辞を除く各値はDICOMから読みます。必須値がない場合、別の識別子へ黙って置換せずエラーにします。

```text
{prefix}_{PatientID}_{SeriesNumber}_{StudyDate}_{StudyTime}_{InstanceNumber:04}_{SOP suffix}.png
{prefix}_{PatientID}_{SeriesNumber}_{StudyDate}_{StudyTime}_{InstanceNumber:04}_{SOP suffix}.mp4
```

静止画のタスク名は次の形式です。Study suffixはStudyInstanceUIDのピリオドを除いた末尾8桁です。8桁未満の場合は全桁を使います。Series単位ではなく、同じStudyの静止画を一つにまとめます。マルチフレームDICOMは、上記MP4名から拡張子を除いた名前で、一つの動画タスクにします。

```text
{prefix}_{PatientID}_{StudyDate}_{Study suffix}
```

タスク名とファイル名の `{prefix}_{PatientID}` では、PatientIDが既に `prefix` とアンダースコアで始まる場合、接頭辞を重ねて付けません。例えば接頭辞が `ABC` なら、`ABC_DEFGH` はそのまま使い、`ABCDEFGH` は `ABC_ABCDEFGH` にします。大文字と小文字は区別し、先頭以外に接頭辞が含まれるだけでは省略しません。前後の空白を除いた元の値で判定するため、ファイル名用の文字置換で生じたアンダースコアはこの判定に使いません。DicomTagのPatientIDは元の値を保存します。

## 画像と動画の変換

ドプラ、カラー、エラストグラフィなどをDICOMタグの値で除外する条件はありません。画像でないDICOMや、対象外の通常ファイルは読み飛ばします。タスクを特定できた画像DICOMの変換失敗は、そのタスク全体の失敗として記録し、他のタスクの変換は続けます。失敗したタスクの一部の画像だけを登録することはありません。タスクの特定に必要な項目が欠けている場合や、入力アーカイブ自体が不正な場合は、取り込み全体を失敗にします。

PNGでは、8ビットに収まらない整数を16ビットで保存します。負値がある場合は最小値を引きます。16ビットの範囲を超える画素や浮動小数点画像は拒否します。Window、Rescale、MONOCHROME1の反転は適用しません。DICOMの元の画素値と表示用PNGの値が常に同一という仕様ではありません。RGBの並びはPNGエンコーダーに合わせて変換します。

PALETTE COLORは未対応です。画素値が色の索引であるため、そのまま単色画像として保存せず、取り込みをエラーにします。カラーLUTの適用は行いません。

動画はMP4へ変換します。FrameTime、FrameTimeVectorの正の値の中央値、CineRate、RecommendedDisplayFrameRate、30 fpsの順にフレームレートを決めます。符号なし8ビットの動画は、1フレームずつ復号して書き込みます。それ以外の動画は、最初の走査で動画全体の最小値と最大値を求め、次の走査で各フレームを同じ範囲で8ビット化します。全フレームの画素配列を保持せず、従来と同じ動画全体の明るさの対応を維持します。

内包されたMPEG2、H.264、H.265の動画は、CVATが利用するPyAVで復号します。DICOM内の分割された動画データを元ファイルから直接読み、動画全体を一時ファイルへコピーしません。H.264のFragmentable転送構文など、4 GiBを超える動画を分割して格納する形式も対象です。H.265 Main 10は10ビットの値を保持してから、動画全体の範囲で8ビット化します。立体視用のH.264転送構文には対応せず、音声は取り込みません。

MP4は非可逆圧縮であり、元DICOMの可逆保存ではありません。フレーム数と縦横寸法を再読込で検証し、暗黙の切り詰めを防ぐため奇数寸法の動画は拒否します。内包動画の符号化方式、寸法、ビット深度、フレーム数がDICOMの記述と一致しない場合や、同梱デコーダーで復号できない場合も、そのタスクを失敗にします。

HighBitがBitsStoredから期待される値と異なる場合は、補正前後の復号配列について形状、型、全画素の一致と、BitsStoredの範囲内であることを確認します。一致する場合だけ一つの画像を登録します。元DICOMのHighBitをTagに残し、補正版の別画像は生成しません。

## 重複の扱い

取り込み時にプロジェクトの既存タスク名と照合し、同名タスクは重複エラーとして登録対象から外します。完全なStudyInstanceUIDが一致する場合も、既存タスクへ追加や上書きはしません。UIDが異なる場合や確認できない場合は、その件数も結果に示します。同じ入力内で異なるStudyInstanceUIDから同名タスクが生成される場合は、その名前のタスク全体を失敗として扱い、画像を混在させません。完全なUIDは「DicomTag」に保存します。[検査レポートの取り込み](../extensions/task-guide-import.md)は、同じ「DicomTag」の `PatientID`、`StudyDate`、`Modality` で照合します。

重複や変換エラーがあるタスクと登録可能なタスクが混在する場合は、登録可能なタスクだけを保存します。一部成功の通知には、`WARNING: DICOM:` から始まる集計を警告として表示します。全件が重複などで失敗した場合は、RequestsをFailedとして扱い、エラー通知を表示します。結果には作成数、失敗数、重複名の数などを表示し、患者IDやタスク名は記録しません。

既存タスクへの画像追加やアノテーション更新は行いません。変換後にプロジェクト行をロックして名前とUIDを再確認し、このインポーター同士の同時登録を直列化します。通常のCVATタスク作成APIには新しい一意制約を加えていないため、別経路で同名タスクを同時作成する操作までは禁止しません。

静止画は新規タスクごとに、生成したPNGのSHA-256とバイト列の一致を確認して重複を除外します。出力名の順に最初の画像を残し、その画像のDICOMタグを採用します。同じ画素でも異なるメタデータを持つ後続画像のタグは統合しません。ハッシュは取り込み中だけ保持し、DB、Tag、マニフェストへ保存しません。既存タスクの画像を読み出して再照合する処理もありません。

同じ出力名かつ同一PNGであれば重複として除外します。同じ出力名なのにPNGが異なる場合、連番を付けたり上書きしたりせず失敗にします。動画同士の入力名衝突は失敗にします。動画内の同一フレームは削除しません。

## 画像に保存するDICOM情報

各静止画と動画の各フレームに、標準のTagアノテーション `DicomTag` を追加します。既知の標準タグには、`PatientID`、`PixelSpacing`、`StudyInstanceUID` などの標準属性名（Keyword）を使います。Keywordがないタグとprivate tagは `00111010` のような8桁の16進タグ番号を使います。複数のタグ番号が同じKeywordを持つ繰り返しタグは、`OverlayRows_60000010` のように番号を付けて区別します。入力型は `text` です。ファイルメタ情報とデータセット直下の単純値を対象にし、Sequence、バイナリ値、解釈できないVRは除外します。入れ子は展開しません。複数値はDICOMと同じバックスラッシュ区切りで保存します。数値もテキストとして保持します。

プロジェクトにない属性だけを追記し、既存の属性、他のラベル、既存のアノテーションは置き換えません。既存のDicomTagの属性は、今回の入力にないものも含めてすべてTextである必要があります。Text以外の属性があれば、空文字の保存によって後の出力を壊さないよう、保存前に失敗にします。文字列はCVAT本体の属性値の制約により4096文字までで、超過値やNULを含む値を黙って切り捨てません。長い `FrameTimeVector` などがこの上限を超える場合も、そのタスクを失敗にします。これはDICOMファイルの容量とは別の制約です。CVATが採番した画像パスとフレーム番号を照合してTagを付けるため、入力順をそのままフレーム番号とみなしません。

`components/dicom_import/dicom_keywords.json` にタグ番号とKeywordの対応を保存しています。取り込みにはこの対応を使い、pydicomの辞書更新によって既存の属性名が変わらないようにしています。回帰テストは固定タグと繰り返しタグの対応をpydicomの辞書と照合するため、更新時の追加、削除、変更を検知できます。対応表を更新する場合は差分を確認します。

そのDICOMにない属性には空文字を明示します。これにより、既存ラベルの既定値が画素間隔や患者識別子として補完されることを防ぎます。既存ラベルの既定値自体は変更しません。

新規属性は `mutable=false` です。ただし、これはTrackでフレームごとに値を変えるかどうかの設定であり、編集禁止ではありません。読み取り専用にはしておらず、APIによる変更も禁止していません。 DICOMタグは標準の権限で編集でき、標準の置換インポートで削除される可能性もあります。既存データの保存方式やAPI契約を変えない取り込み機能として分離しています。

患者識別情報も指定どおりファイル名とTagへ保存します。匿名化機能ではありません。アクセス範囲と保存先は通常のCVAT運用で管理します。

## 制約と障害時の動作

ブラウザーはフォルダ全体のZIP作成やCRC32計算を行いません。ファイルの一覧とサイズを先に登録し、各ファイルを最大16 MiBに分け、最大4ファイルを並列に送ります。フォルダ全体や単一ファイルを一度にメモリーへ読み込まず、受信側も分割されたデータを順にディスクへ書き込みます。1回の入力は既定で合計1 TiB、100,000ファイルまでです。60 GBや200 GBのフォルダ、4 GiBを超えるZIPやTARも、この転送方式の対象です。

サーバーは受信した通常のDICOMをその場所から読み、取り込み前に全入力を再コピーしません。入力にZIPやTARが含まれる場合だけ展開します。展開時に書き出す合計は既定1 TiB、100,000エントリー、入れ子3段までです。入れ子のアーカイブでは、中間アーカイブとその中身の両方を展開量へ計上します。通常ファイルの転送容量と展開量は別に制限します。上位ディレクトリ参照、絶対パス、リンク、特殊ファイル、暗号化ZIP、同じ展開先への重複を拒否します。

画像変換には、DICOMファイル全体や全フレームの画素配列の合計に対する1 GiBの上限はありません。受信済みファイルから1フレームずつ復号し、動画全体を画素配列へ展開せずに変換します。復号後の1フレームだけに、既定1 GiBの上限を適用します。この値は `CVAT_DICOM_MAX_FRAME_BYTES` で変更でき、通常の解像度でフレーム数が多い動画には影響しません。入力全体には転送容量の設定が引き続き適用されます。新規メディアの保存先はローカルストレージに限定します。[^decoder-memory]

Deflated Explicit VR Little Endianでは、データセットを順に一時ファイルへ展開してからフレームを読みます。展開結果の容量には、DICOMごとに `CVAT_DICOM_MAX_EXPANDED_BYTES` を適用します。アーカイブの合計展開量とは別の検査です。

保存先には、受信ファイル、アーカイブやDeflated DICOMの展開結果、変換したPNGやMP4、CVATが生成する画像チャンクのための空き容量が必要です。転送開始時に元ファイル分の空き容量を確認しますが、予約はしません。並行処理による使用量の増加や、変換後の容量増加はこの確認では保証できません。登録が済んだタスクの変換用一時ファイルは順次削除しますが、すべての変換を終えてからタスク登録を始めるため、変換結果全体を置く容量も必要です。

転送途中の通信エラーは回数を制限して自動再試行します。未受付の転送データは中止時の清掃対象で、通信断などで中止要求が届かなかった場合もCVAT標準の一時領域の保存期間で清掃します。転送中とキューの待機中、取り込み実行中のデータはロックと処理状態を確認して清掃から保護します。処理終了後は元ファイルを削除し、受付を再確認するための小さな記録を一時領域の保存期間まで保持します。

外部のリバースプロキシにも、少なくとも16 MiBのリクエストを通す容量設定が必要です。接続やリクエストのタイムアウトは、一つの分割データを転送できる長さに設定します。200 GBのフォルダを一つのHTTPリクエストで受け取る設定は不要です。

入力の読み出しは命名確認と画素変換で分け、変換済みDICOMの画素キャッシュを次の入力へ持ち越しません。キューの実行開始時と変換後に、利用者の有効状態、組織、プロジェクトの次元と標準のデータセット取り込み権限を再確認します。

DB更新は標準のプロジェクト取り込みトランザクション内で行い、各タスクの登録に保存点を設けます。タスク固有の検証エラーや登録エラーでは、そのタスクのDB更新と新規メディアを取り消し、他のタスクを続けます。権限の失効、共有ラベルの不整合、保存先の障害、結果の保存失敗など、取り込み全体に関わる例外は全体を失敗にし、新規メディアディレクトリを清掃します。プロセスの強制終了やホスト障害までファイルの原子性を保証するものではありません。標準のバックアップや保守手順は引き続き必要です。

受付確認中に画面を閉じた場合は、Requestsを確認してから新しく取り込みます。再取り込みで既存タスク名が一致すると重複エラーになるため、同じStudyへの追加画像を後から取り込む用途には使えません。

## 管理者向けの設定

既存の設定を保持したまま、`.env` の `CVAT_EXTENSIONS` に `dicom_import` を追加します。[更新手順](../extensions/update.md)に従って、管理コマンドでサーバーとUIを再ビルドし、起動してください。追加サービスやGPUは不要です。

選択を外して再ビルド、再起動すると、画面の入口と取り込みが無効になります。登録済みの画像、動画、タグは標準のデータとして残ります。DICOM用パッケージは共通サーバーイメージに含まれるため、機能の選択解除だけではパッケージを取り除きません。

容量と実行時間は、同じ `.env` で設定します。値は正の整数です。`cvatctl config` と `cvatctl doctor` は適用値を表示し、サーバーと取り込みワーカーの設定が一致していることを確認します。

| 設定 | 既定値 | 対象 |
| --- | --- | --- |
| `CVAT_DICOM_MAX_UPLOAD_BYTES` | `1099511627776`（1 TiB） | 1回に転送する元ファイルの合計バイト数 |
| `CVAT_DICOM_MAX_UPLOAD_FILES` | `100000` | 転送ファイル数と、アーカイブ展開時のエントリー数。それぞれに適用 |
| `CVAT_DICOM_MAX_EXPANDED_BYTES` | `1099511627776`（1 TiB） | アーカイブ展開で書き出す合計バイト数。Deflated DICOMでは、個々のデータセットを一時ファイルへ展開する容量にも適用 |
| `CVAT_DICOM_MAX_FRAME_BYTES` | `1073741824`（1 GiB） | 復号後の1フレームの画素配列。DICOMファイル全体や全フレームの合計には適用しない |
| `CVAT_DICOM_IMPORT_TIMEOUT` | `86400`（24時間） | 受け付けたDICOMの変換と登録の実行時間。転送時間とキューの待ち時間は含まない |

DICOMの実行時間は、この拡張の取り込みだけに適用します。他の形式の標準取り込みタイムアウトは変更しません。容量や時間の設定を変更した場合も、既存の `cvatctl down`、`up`、`check` の手順で反映します。

## 開発者向けの実装と確認

登録は標準のプロジェクト用データセット取り込みAPIとキューを使います。一つの入力から複数タスクを作るため、プロジェクトのActionsを入口としています。タスク用やジョブ用のアノテーション取り込みには、この形式を指定できません。新しい認証経路やDBマイグレーションは追加しません。

転送の受付には既存の `POST /api/projects/{id}/dataset` へ `format=DICOM 1.0` と `dicom_upload` を指定します。`dicom_upload` の操作は `start`、`files`、`chunk`、`finish`、`status`、`cancel` です。既存のプロジェクト用取り込み権限を毎回確認し、転送の記録は利用者、プロジェクト、組織に結び付けます。ファイル一覧は500件ずつ登録し、大きなJSONを一括送信しません。サーバー生成の受付記録を入力として、標準の取り込み処理へ渡します。

変換、アーカイブ、転送の管理、標準保存との接続は `components/dicom_import/`、画面は `cvat-ui/plugins/dicom-import/` です。本体には、既存APIから転送処理へ渡す入口と、生データを一括展開しないパーサーの指定、一時領域の清掃から処理中の転送を保護する入口を加えます。標準TUSのファイル上限や完了時の記録削除を全機能向けに変更する代わりに、DICOMの処理だけをこの入口へ分けています。独立したサービスやキューは追加しません。

完了通知へ集計を渡すため、標準Request APIが完了したDICOM取り込みのメッセージを返します。プラグインは既存の `core.requests.listen` で結果を受け取ります。Requests画面の描画は標準の実装を使います。拡張管理は `components/*/extension.json` から既存カタログへ登録します。ヘッダー確認と変換、タスク登録の割合は各段階の処理件数に基づく値であり、残り時間の予測ではありません。進捗保存は段階の切り替え時と原則0.5秒間隔に制限します。

単体テストは合成データを使用します。pydicomが導入されている環境では、合成DICOMの書き出しから復号、PNG重複除外、動画変換までを実行します。MPEG2、H.264、H.265の試験にはCVATサーバーと同じPyAVも必要です。必要な依存がない場合、そのテストモジュールはスキップします。保存接続の試験ではORM、RQとOPAを代替実装にし、Data、Task、Jobの保存先メソッドは実モデルのソースから読み込みます。ディレクトリの清掃、タスク単位の保存点、一部失敗と全件失敗、最終status保存時の失敗、権限剥奪後の拒否、完了メッセージと結果通知、ダイアログを閉じた後の通知、アカウント変更時の通知抑止を確認します。これらの試験を、稼働中のCVATでの結合試験と区別してください。

転送の試験には、2 GiBと4 GiBを超えるサイズや200 GiB相当のファイル一覧、分割範囲、同時転送数、受信応答の消失、再送、受付の重複、所有者の不一致、中止と清掃を含めます。大容量のメタデータや疎ファイルを使う確認は、同容量の実転送試験とは区別します。本体接続の試験では実際のルーティングとパーサー、権限に渡す操作範囲、キューへ渡す内容を確認し、OPAの判断とRedisは代替実装を使います。

変換の容量検証には、1 GiBを超える元ファイルと復号後の動画、1フレームの設定値の境界、4 GiBを超える内包動画の位置管理と断片をまたぐ読み取りを含めます。フレームごとの色、動画全体の濃度変換、破損時の後始末、Deflatedの段階的な展開も確認します。画素配列全体を読み込む呼び出しが使われないことを検査し、圧縮形式ごとの合成動画で実際の復号とMP4出力を確認します。

実環境への反映前には、Composeビルド、UI全体の型検査とブラウザー操作、実CVATへの権限別取り込み、同時取り込み、途中失敗後のDBとファイルの確認、実際の圧縮DICOM、標準バックアップの復元を確認します。大容量の受入確認では、60 GBと200 GBのフォルダについて、転送開始までの待ち時間、受領バイト数と表示の一致、受付後にブラウザーを閉じた際の継続、ネットワーク切断からの再開、転送速度、メモリーと一時領域の使用量を記録します。
