# タスクの説明を一括登録する

[アノテーション操作](../annotation/README.md) / [追加機能の一覧](../README.md)

複数タスクの作業説明や検査レポートを、ZIPファイルからまとめて登録する機能です。保存先には、CVAT標準の説明文と添付ファイルを管理する機能 **AnnotationGuide** を使います。登録した「AnnotationGuide」は、[タスク情報の表示](task-context.md)から確認できます。

## 取り込み形式を選ぶ

対象プロジェクトの `Import dataset` で、次の形式を選び、ZIPファイルを指定します。アノテーションを登録する `Import annotations` とは入口が異なります。3形式とも既存のZIPアップロード、インポートキュー、Requestsを使用します。各形式はプロジェクトへの取り込みに対応し、タスクやジョブへの取り込みはエラーになります。

| 形式 | 入力 | 対象タスクの指定 |
| --- | --- | --- |
| `Task Guide JSON 1.0` | タスク名をキー、Markdown本文を値とするJSONを1件入れたZIP | タスク名の完全一致 |
| `Task Guide Markdown Zip 1.0` | タスク名と同名の `.md` ファイルをまとめたZIP | 拡張子を除くファイル名の完全一致 |
| `Task Guide DICOM Report Import 1.0` | 医療レポート用JSONを1件入れたZIP | 画像に保存したDICOMの検査識別子で照合 |

取り込み先は各タスクの標準 `AnnotationGuide` です。プロジェクト用ガイド、画像、動画、ラベル、Tag、Shape、Trackは変更せず、新規タスクも作成しません。汎用JSONとZIPはDICOM以外のタスクにも使用でき、タスクに画像や動画が未登録でもガイドを登録できます。

JSONを使う2形式では、UTF-8のJSONファイルを1件だけZIPに入れます。ZIP内のフォルダは許可しますが、JSONが複数ある場合、JSON以外のファイルがある場合、JSONファイルがない場合はエラーです。JSONファイル名は任意で、`.json` と `.JSON` を受け付けます。アップロードするファイルの拡張子は、標準の取り込みと同じ `.zip` にしてください。

## タスク名と本文をJSONで指定する

ZIPに入れるJSONのキーにタスク名、値にMarkdown本文を指定します。タスク名は大文字小文字と空白を含めて完全一致で照合し、接頭辞やUIDを推定しません。

```json
{
  "task_001": "# 作業説明\n\n対象を囲んでください。\n",
  "task_002": "## 注意事項\n\n- 境界を確認してください。\n"
}
```

JSON文字列中の改行は `\n` で表します。JSONを読み込んだ後は実際の改行を含むMarkdownとして保存されます。本文をエスケープしたり、見出しや管理用コメントを加えたりしません。空文字列を指定すると、そのタスクのガイド本文は空になります。

## タスクごとのMarkdownファイルをまとめる

各タスクのMarkdownをUTF-8の `task名.md` ファイルとして保存し、ZIPにまとめます。ファイル中には通常の改行を記述します。UTF-8のBOMは受け付けます。

ZIP内のフォルダは許可し、フォルダを除いたファイル名からタスク名を決めます。例えば `guides/task_001.md` は `task_001` に対応します。同じタスク名に対応するファイルが複数あれば、内容が同じでもエラーです。`.md` と `.MD` を受け付けます。タスク名に `/` などファイル名に使えない文字がある場合はJSON形式を使用してください。

ZIPにはMarkdownファイルとフォルダだけを含めてください。絶対パス、親フォルダへの参照、シンボリックリンク、暗号化されたファイルは拒否します。ZIPの内容はファイルシステムへ展開せず、直接読み取ります。

## 汎用JSONとZIPの照合と再取り込み

対象プロジェクトに同名のタスクが複数ある場合は、更新先を決められないため全体をエラーにします。該当タスクがない項目はスキップし、全件が未一致ならエラーです。一部が未一致の場合は一致したタスクの更新を完了します。

汎用JSONとZIPでは、入力のMarkdownで対象ガイドの本文全体を置き換えます。以前の手書き部分やDICOMレポートの自動生成部分も置換対象です。保持したい本文や添付ファイルの参照は、入力のMarkdownにも含めてください。同じ本文を再取り込みした場合は、本文と更新日時を変更しません。

CVATの管理する添付ファイルへの `(/api/assets/{UUID})` 参照は、取り込み先の既存ガイドに属する添付だけを受け付けます。新規ガイドへの管理添付参照、別ガイドの添付、存在しない添付があれば、ガイドを一つも書き込まずにエラーにします。添付ファイルのコピーやZIPからの登録は行いません。外部URLへの画像参照やリンクは入力のまま保存します。DICOMレポート形式で保持する既存の手書き本文は、この追加検証の対象にはしません。

## 検査レポートをJSONで指定する

ZIPに入れるJSONは、`records` 配列を持つオブジェクト、またはレコード配列です。各レコードは `input` と `result` を持ちます。処理は機械的で、翻訳、医学的な要約、部位辞書、外部サービスへの送信は行いません。

```json
{
  "records": [
    {
      "input": {
        "patient_id": "P1",
        "study_instance_uid": "1.2.3",
        "study_date": "20250101",
        "parsed_patient_age": "25Y",
        "patient_sex": "M",
        "modality": "CT"
      },
      "input_text": "History: History text\nFindings: English findings\nImpression: English impression",
      "result": {
        "extracted": {
          "part": ["brain"],
          "history": ["History text"],
          "objective": "Objective text",
          "findings": "English findings",
          "impression": "English impression"
        },
        "findings_ja": "所見本文",
        "impression_ja": "診断本文"
      }
    }
  ]
}
```

識別子は文字列で指定します。次の別名を受け付けます。

| 項目 | 受け付けるキー |
| --- | --- |
| 患者ID | `patient_id`、`pid` |
| StudyInstanceUID | `study_instance_uid`、`study_uid`、`uid` |
| 検査日 | `study_date`、`date`、`dt` |

`uid` はStudyInstanceUIDの別名です。患者IDには使用しません。同じ項目の別名が併存し、値が異なる場合は拒否します。検査日は次の形式を8桁の `YYYYMMDD` に変換してから比較するため、表記だけが異なる同日の別名は受け付けます。

| 入力形式 | 入力例 | 正規化した検査日 |
| --- | --- | --- |
| 8桁の数字 | `20250107` | `20250107` |
| 年から始まる区切り付き日付 | `2025-01-07`、`2025/1/7`、`2025.01.07` | `20250107` |
| スペースまたは `T` で時刻を続けた日時 | `2025-01-07 00:00:00`、`2025-01-07T00:00:00+09:00` | `20250107` |
| RFC形式の日時 | `Tue, 07 Jan 2025 00:00:00 GMT` | `20250107` |

区切り付き日付では、年は4桁、月日は1桁または2桁で、2か所の区切りを同じ文字にします。時差付き日時も、書かれた年月日を使用し、UTCなどへ時差変換しません。`01/07/2025` のように月日を推測する必要がある形式や、存在しない日付は拒否します。

2種類の入力例は [structured_report.json](../../tests/python/unit/fixtures/task_guide/structured_report.json) と [ptc_report.json](../../tests/python/unit/fixtures/task_guide/ptc_report.json) にあります。架空データから必要な項目だけを残した回帰テスト用のJSONで、RFC形式の日付、日時、別名の組み合わせ、末尾に先頭ゼロを含むUIDを確認できます。取り込み時はどちらかのJSONを1件だけZIPに入れます。

## DICOMレポートとタスクの照合

DICOMの検査を識別する `StudyInstanceUID` の完全一致を使います。このフォークでは、DICOMの識別情報や撮影条件を画像単位で保存したタグを **DicomTag** と呼びます。レポートは、この「DicomTag」にある省略されていない識別子と照合します。PatientIDや日付だけの照合、部分一致、SOP UID末尾8文字からの推定は行いません。接頭辞の指定は不要です。

静止画と動画のどちらも、Tagアノテーション `DicomTag` の完全なUIDを参照します。使用する属性は `StudyInstanceUID`、`PatientID`、`StudyDate` です。静止画タスク名のStudy UID末尾8桁からは照合しません。JSONにPatientIDや日付があれば、タグとの一致も確認します。

タスク名からUIDや患者ID、日付を推定しません。Keyword名のDicomTagに完全なUIDが保存されていれば、タスク名の変更後も照合できます。

患者IDに接頭辞が含まれる場合も、DICOMとJSONの元のPatientIDを比較します。例えば両方が `ABC_DEFGH` なら、DICOM取り込みで接頭辞 `ABC_` の重複付与を省いても照合できます。タスク名に付けた接頭辞はDicomTagのPatientIDを変更しません。DICOMが `ABC_DEFGH`、JSONが `DEFGH` の場合は不一致として拒否し、接頭辞を推測して取り除きません。

一つのStudyに静止画タスクと複数の動画タスクがある場合、そのStudyのガイドを該当する全タスクへ付与します。複数の接頭辞で登録された同じStudyも同様です。プロジェクト外のタスクは検索しません。

タスク内に複数のStudy UIDが混在する場合、患者IDや日付が矛盾する場合、同じStudyについて異なる入力内容が重複する場合は、全体を失敗させます。同じ識別情報と同じ生成本文を持つ重複レコードは一つにまとめます。

該当タスクのないレコードはスキップします。全件が未一致の場合はエラーです。件数とJSON配列中の位置は取り込みジョブの内部statusに保存しますが、標準のRequests画面は完了後にこの要約を表示しません。患者識別子や所見本文はstatusに出力しません。

## DICOMレポートから生成する本文

```markdown
# 概要
- 年齢：25Y
- 性別：M
- 検査方法：CT

## 検査概要
- 検査部位：brain
- 既往歴：History text
- 検査目的：Objective text

## 所見
所見本文

## 診断
診断本文

## 参考生データ
History: History text
Findings: English findings
Impression: English impression
```

概要では次の順に最初の空でない値を使用し、値をそのまま表示します。月齢を年齢へ換算したり、性別コードや検査方法を独自に翻訳したりしません。

| 表示項目 | `input` 内の参照順 |
| --- | --- |
| 年齢 | `parsed_patient_age` → `age` |
| 性別 | `patient_sex` → `sex` |
| 検査方法 | `modality` → `mod` |

検査概要では `result.extracted.part` を「検査部位」、`history` を「既往歴」、`objective` を「検査目的」として表示します。配列は順番を保って改行で連結します。

所見と診断は独立に、`result.*_ja`、`result.*_jp`、`result.extracted.*`、`result.*_en`、`result.*` の順で最初の空でない値を使います。日本語がない側だけ英語へ切り替えます。

参考生データには、各レコードの `input_text` を本文の最後に表示します。文字列またはnullを受け付け、項目がない場合、null、空文字列、空白だけの場合は見出しごと省略します。数値や配列など文字列以外の値は拒否します。改行を保持し、他の本文と同じようにMarkdownやHTMLの記号をエスケープして文字として表示します。

その他の項目もnull、空文字列、空配列は省略します。ただし所見と診断の見出しは残し、本文がない場合は「記載なし」とします。参考生データを含め、選択対象の内容が全て空ならエラーにします。入力の改行は保持し、MarkdownやHTMLの記号は文字として表示するためにエスケープします。患者ID、Study UID、日付、施設情報、APIの解析結果、処理時間などを独立した項目として本文に追加しません。ただし `input_text` に含まれる情報は参考生データの一部として表示します。

## DICOMレポートの再取り込み

初回は次の不可視コメントで囲んだ本文を追加します。既存ガイドがある場合、その内容の後ろに追加します。

```markdown
<!-- cvat:study-report:start -->
生成した本文
<!-- cvat:study-report:end -->
```

再取り込みでは囲まれた範囲だけを置き換えます。前後の手書き本文と既存の添付参照は保持し、同じ内容なら保存も行いません。自動生成範囲の中を手編集した場合、その変更は次の取り込みで置き換わります。手書きの追記は範囲の外へ置いてください。コメントが欠けている場合や複数ある場合は、既存本文を推測で消さずにエラーにします。

## 管理者向けの設定

サーバー、インポートワーカー、UIを同じ版に再ビルドしてください。取り込み形式は既存のバックエンド登録に追加され、常時利用できます。`cvatctl` の `task_context` はタスク詳細とInfoでの表示を選択する拡張で、取り込み形式の有効化スイッチではありません。追加サービスやGPUは不要です。設定と配備は[拡張機能の管理](management.md)を参照してください。

## 開発者向けの権限と保存

キュー実行時にプロジェクトが投入時と同じ組織に属していることと、実行者が現在も標準のプロジェクトインポート権限を持つことを確認します。さらに、実行者の現在の権限で各タスクの標準 `AnnotationGuidePermission` を確認します。未作成のガイドには作成権限、既存のガイドには更新権限が必要です。キューの利用者情報がない場合や利用者が無効になっている場合も拒否します。

全対象の照合、権限、生成本文を検証してから保存します。標準DBトランザクションと行ロックを使い、保存途中に例外が発生した場合はDB変更をロールバックする構成です。各Task Guide形式とDICOMインポーターはプロジェクトの行ロックで直列化します。通常のUIによる手編集との同時更新を、独自の版管理で調停する機能は追加していません。

ガイドを新規作成または変更したタスクと、その親プロジェクトの更新日時も同じトランザクション内で更新します。標準バックアップはこの日時でキャッシュを区別するため、取り込み後のタスクバックアップとプロジェクトバックアップには最新のガイドが含まれます。同じ内容を再取り込みしただけの場合は、ガイドも更新日時も変更しません。

独自DBテーブル、マイグレーション、API、依存パッケージ、サービスは追加しません。形式の登録には既存の `formats/registry.py` への接続を使います。3形式ともZIPを受け取るため、標準の取り込み画面、クライアント、アップロードのZIP検証を変更する必要はありません。

## 制限と検証

ZIPと展開後のJSONは32 MiBまでです。ZIPは展開後の合計も32 MiBまでで、フォルダを含めて50,000エントリーまでです。JSONは50,000タスクまたはレコードまでです。保存するガイド本文は1,000,000文字までで、DICOM形式では既存本文も含めた上限です。重複JSONキー、不正Unicode、NUL、非有限数、対応外の値の型は拒否します。

次のコマンドで追加テストを実行します。

```sh
python -m unittest discover -s tests/python/unit -p test_task_guide_import.py -v
```

回帰テストでは3形式の登録と読み込み、Markdownの維持と置換、完全一致と同名タスクの拒否、JSON1件を入れたZIP、ZIPのサイズ上限と不正なパスの拒否、短縮タスク名と完全なUIDによる照合、Keywordによる識別を確認します。インポート接続のテストはORM、OPA、RQを模擬します。キュー待機中の組織変更とプロジェクト取り込み権限の失効によって書き込みが拒否されることも確認します。

DICOMレポートでは、2種類の入力例、識別子の別名と矛盾の拒否、各日付形式の正規化、接頭辞を含む患者IDの照合、概要の別名、既往歴の見出し、参考生データの表示とエスケープも確認します。

バックアップの回帰テストでは、標準の `create_backup()` をソースからそのまま取り出して実行します。取り込み前のZIPをキャッシュに残した状態でガイドを作成または更新し、タスクとプロジェクトの再バックアップに最新の本文が含まれることと、同じ内容の再取り込みでは既存キャッシュを再利用することを確認します。ZIPの読み書きは実行しますが、DB、Exporter、ロックは代替実装です。

これらの代替実装を使う試験では、実CVAT、PostgreSQL、権限判定サービスのOPA、処理キューのRQ、ブラウザーを接続した動作は確認できません。実環境では、プロジェクトの取り込み画面からZIPを送信し、Requestsの結果、タスクのInfo、画像と既存アノテーションの維持、権限不足時の非更新を確認してください。
