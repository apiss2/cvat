# 実行権限と情報の保護

## 登録権限の対象

この構成は、モデルの実行コードを作成する権限を持つ、管理されたチームメンバーを対象にします。
登録できるのはONNX重みだけでなく実行可能なPythonコードであるため、認識精度、ファイル操作、実行時間、ログへ出す内容をモデル作成者が確認します。

登録権限は、標準構成ではCVATで認証できる全ユーザーに与えます。
CVAT側で自由な新規登録を許可すると、そのユーザーにもモデルコードを登録する権限が生じます。
不特定の第三者を受け入れるサービスとして運用する場合は、この構成の登録範囲をそのまま使わず、組織の権限管理に合わせた制限を先に設けます。

推論ワーカーにはLinuxコンテナによる制限を設けます。
ただし、未知の脆弱性やGPUドライバーの問題まで含めて、敵対的なコードからホストを完全に保護することは保証しません。
登録権限の対象を決める際は、コンテナだけで任意の第三者のコードを安全に実行できるとは扱わないでください。

## CVATのセッションによる認証

管理サーバーは、ブラウザーから受け取ったCVATのセッションCookieを、管理者が指定した `MR_CVAT_URL` の `GET /api/users/self` へ転送して利用者を確認します。
Cookie名は `MR_CVAT_SESSION_COOKIE` で指定し、既定は `sessionid` です。
HTTPの`Host`と`X-Forwarded-Proto`は、管理者が設定した`MR_PUBLIC_URL`のホストとスキームから作成します。
この設定により、CVATへ内部ネットワークで接続しながら、Djangoには正しい公開ホストを伝えます。
他のCookie、ブラウザー指定の認証接続先、任意の転送ヘッダーは使用しません。
CVATのパスワードと個人用トークンは受け付けず、保存もしません。
CVAT本体のコードの変更や取り込みは行わず、既存のHTTP APIだけを使用します。
新規アカウントの登録可否、パスワードの変更、利用停止はCVATの運用に従います。

管理者の判定は、CVATのユーザー情報で `is_superuser` が真、または所属グループに `admin` が含まれる場合です。
`is_staff` だけではモデル管理の管理者権限を与えません。
それ以外の利用者は自身のモデルを管理できます。

管理API要求は、その都度CVATへユーザー情報を照会します。
有効なセッションがない場合は401、CVATでのアクセス拒否や利用停止の場合は403を返します。
CVATが照会を400または406で拒否した場合は連携エラーとして502を返し、応答本文で公開ホスト設定の確認と応答形式の不一致を区別します。
通信障害や、それ以外の予期しない応答は503を返します。
管理サーバーが過去の照会結果だけで利用を継続させることはありません。

モデルの所有者はユーザー名で記録します。
CVATのユーザー名を変更しても、既存モデルの所有者名は自動的に変わりません。
退職者の名前を別の人へ再利用すると過去のモデルの所有者と一致するため、モデルを保持する間はユーザー名を再利用せず、名称変更が必要な場合は管理者が所有権と保存データの移管を別途確認します。

## ブラウザーのセッションと操作の保護

セッションの発行、Cookie属性、有効期間、失効はCVATが管理します。
CVAT画面とモデル管理画面は同じオリジンに置き、CVAT標準のCookieパス `/` で `/model-registry/` にもCookieが送られる構成にします。
管理サーバーは専用のCookieを発行せず、CVATのCookieを管理画面のJavaScriptや `localStorage` へ取り出しません。
管理サーバーを再起動しても、CVATのセッションが有効なら管理画面を使い続けられます。
共有端末ではCVATからログアウトします。

登録、更新、削除などの操作では、`Origin` が `MR_PUBLIC_URL` のオリジンと完全に一致し、`X-Registry-Request: 1` が付いていることを確認します。
この独自ヘッダーを付けられない外部サイトのフォームからの送信を拒否し、外部オリジンからのCORS要求を許可しません。
管理画面専用のCSRFトークンは発行しません。
リバースプロキシの設定で要求の `Origin` を固定値へ置換せず、利用者のブラウザーから来た値をそのまま転送します。
`Cookie`、`X-Registry-Request`、`X-Registry-User-ID` も転送します。

画面からの更新要求には、表示中の利用者を示す `X-Registry-User-ID` も付けます。
CVATのセッションが別の利用者に切り替わっている場合は、アップロード本文の読み取り前に409で拒否し、画面の利用者情報を更新します。
元の操作は自動的に再実行しません。
このIDは権限を与える値ではなく、操作する本人は引き続きCVATのセッションで確認します。
この任意ヘッダーを送らないCLIなどは、送信したCookieの利用者として操作します。

公開URLには利用者が実際に開くCVATのURLを指定します。
別ホストの管理画面を直接開いたり、設定と異なるホスト名でアクセスしたりすると、認証や操作時の検査が一致しません。
通常の利用者にはCVAT上部のモデル管理リンクを案内します。

## モデルの公開範囲

認証済みの利用者は他のメンバーが公開したモデルの説明とラベルを閲覧できます。
作者名は所有者として記録したユーザー名を表示し、連絡先は登録者が `author_contact` に記入した内容だけを公開します。
CVATのプロフィールからメールアドレスを自動取得して表示する処理はありません。

更新、削除、試験推論、過去の版、登録処理の詳細、ログは、所有者と管理者に限定します。
他のメンバーへ一覧を共有することは、重みや実行コード、失敗時の例外、ログを公開することを意味しません。
公開済みのモデルをCVATで実行する権限はCVAT側の推論機能に従い、モデル単位で利用者や組織を限定する機能はありません。

## ワーカーに与える権限

推論ワーカーはUID 65532で起動し、ネットワーク接続、Linux capability、書き込み可能なルートファイルシステムを与えません。
読み取り専用のモデルディレクトリ、専用のUnixドメインソケット用ディレクトリ、容量制限付きの一時領域だけをマウントします。
CVATのデータ、Dockerソケット、アカウント情報、サービス間トークンはマウントしません。

CPU、ホストRAM、プロセス数、読み込み時間、推論時間に上限を設けます。
メンバーはパッケージからワーカーイメージ、マウント先、GPUデバイス、環境変数を指定できず、管理サーバーも提出されたPythonを自身のプロセスへ読み込みません。
GPUメモリには、このRAM上限と同じ容量制限を適用する機能はありません。

ワーカーは入力画像と自身のモデルの重みを読み取れます。
モデルコードがその内容を推論結果やログへ含めることを自動判定する機能はないため、入力データに応じたコードの確認とログの取り扱いが必要です。

## 管理サーバーと通信の権限

管理サーバーはDocker Engineにワーカーを作成させるため、Dockerソケットを使用します。
この操作権限はホスト管理者相当です。
Dockerソケットを読み取り専用マウントにしてもDocker APIの変更操作を禁止できないため、管理サーバー自体を管理者権限を持つ構成要素として管理します。

CVATとは別の推論ホストへ配置すると、登録コードを実行するホストとCVATのデータ保存ホストを分離できます。
この配置でも、推論ホスト、Docker Engine、カーネル、GPUドライバーの更新とアクセス制限は必要です。

ブラウザーから管理画面への接続はHTTPSで保護します。
管理サーバーからCVATのユーザー情報APIへセッションCookieを送る接続も、同じホストのDockerネットワーク内で完結する場合を除き、HTTPSまたは同等に保護した通信路を使います。
別ホストへのサービス間通信も、社内の制限されたネットワークまたはHTTPSで保護し、証明書の検証を無効化しません。

CVATのユーザー情報APIのHTTPS接続に独自の認証局を使う場合は、認証局のPEM証明書を `MR_CONFIG_DIR/ca/cvat-ca.pem` に配置します。
同じホストでは共通の`.env`へ`MR_CVAT_CA_FILE=/config/ca/cvat-ca.pem`を設定し、停止済みの構成を`cvatctl up --no-build`で再開します。
別の推論ホストでは、そのホストの`registry.env`へ設定します。
中継から推論ホストへの接続に使う `CVAT_MODEL_REGISTRY_CA_FILE` とは別の設定です。
いずれも証明書の検証を有効にしたまま、接続先に対応する認証局を指定します。

中継サービスと管理サーバーはホストの公開ポートを持ちません。
プロキシから管理サーバーへはDockerネットワーク上の内部ポート8091で接続します。
`/internal/*` の認証には専用のサービス間トークンを使用し、CVATユーザーのセッションからは利用できません。
公開プロキシではブラウザーに必要な管理経路だけを転送し、サービス間の経路は許可したCVATサーバーからだけ到達できるようにします。

## 保存データとサービス間トークン

データ保存先にはPythonコード、ONNX重み、公開前の試験画像、データベース、ログを保持します。
既定の保存先はリポジトリ直下の`cvat-model-registry/`で、その直下に`*`と改行だけの`.gitignore`を作成します。
リポジトリの`.dockerignore`にも除外規則を置き、保存先をGitとDockerのビルド対象から外します。
除外されていてもファイルはホスト上に保存されるため、アクセス権の管理とバックアップは引き続き必要です。
通常の推論画像を保存する機能はありませんが、モデルコードが画像の内容を標準出力へ書けばログに残ります。
バックアップにも試験画像と登録コードが含まれるため、元データと同じ保護を適用します。

モデルの削除は利用停止です。
重みなどの物理削除は、停止状態で管理者が `purge-deleted` を実行します。
バックアップや外部へ保存したログの消去はこの操作に含まれません。
イベントログには件数上限があり、改ざん防止を備えた長期監査保管ではありません。

個人用トークンの認証方式と発行コマンドは提供しません。
既存設定の `MR_AUTH_MODE=cvat` は受理しますが、`token` などの別方式は起動時にエラーにします。
サービス間トークンは中継と管理サーバーの内部通信専用で、利用者へ配布するものではありません。
